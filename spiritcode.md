# SpiritCode — Python CLI для SpiritLM

План отдельного проекта. Согласованные решения зафиксированы 23 октября 2026 года. Реализация CLI и расширений сервера в этот документ не входит.

## 1. Продукт и первая версия

SpiritCode — самостоятельный кодинг-агент для пользователей SpiritLM. Запускается внутри проекта, общается с выбранной моделью, самостоятельно ищет и читает нужные файлы, изменяет код, запускает команды с разрешения пользователя и сохраняет рабочие сессии.

Согласовано:

- Python, поддержка Linux, macOS и Windows.
- Вход только по API-ключу SpiritLM.
- Интерфейс: лента диалога в терминале и строка ввода, без полноэкранного режима.
- Просмотр профиля, баланса, подписки, лимитов и статистики.
- Покупка подписки, пополнение и управление ключами — на сайте.
- Инструкции из `AGENTS.md`, сохранение сессий и автоматическое сжатие контекста.
- MCP, субагенты, IDE-расширения, браузерные инструменты и другие API-провайдеры — после первой версии.

Результат: пользователь устанавливает SpiritCode, вводит ключ, выбирает модель и поручает задачу в существующем репозитории. Указывать каждый файл вручную не требуется.

## 2. Интерфейс и фирменный стиль

При запуске показать жёлтую ASCII-звёздочку с двумя глазами по мотивам `public/icon.png`, название SpiritCode, текущую модель и каталог проекта.

Согласованный пользователем ASCII-рисунок:

```text
          .-.
         /   \
     .--'     '--.
    /     | |     \
    \             /
     '--.     .--'
         \   /
          '-'
```

Использовать обычные ASCII-символы; изображение и специальные терминальные протоколы не нужны. Сохранить исходную иконку как референс в отдельном проекте.

Палитра из `DESIGN.md` SpiritLM:

| Назначение | Цвет |
| --- | --- |
| Тёмный фон | `#080808` |
| Основной текст | `#f3f2ee` |
| Вторичный текст | `#a5a5a1` |
| Акцент, выбор, звёздочка | `#ffe02e` |
| Приглушённые разделители | `#30302e` |

Не менять глобальные настройки терминала. Поддержать truecolor, упрощённые ANSI-цвета и `NO_COLOR`. В узком окне уменьшать шапку, переносить строки и сохранять доступность ввода.

Поведение:

- Потоковый ответ модели, подсветка кода и читаемый Markdown.
- Видимые состояния: ответ модели, чтение, изменение, ожидание разрешения, выполнение команды, ошибка.
- Diff после изменения файлов; команда и рабочая директория перед подтверждением запуска.
- Enter отправляет сообщение, Alt+Enter добавляет строку, стрелки перемещаются по истории.
- Tab дополняет slash-команды и пути; списки моделей поддерживают поиск и выбор клавиатурой.
- Ctrl+C прерывает текущую операцию; в пустой строке ввода повторное нажатие завершает программу.
- Никаких анимаций при перенаправлении вывода; недоверенные ANSI-последовательности из файлов и ответов очищаются.
- Пользовательские сообщения и справка — на русском.

Основные команды:

| Команда | Поведение |
| --- | --- |
| `spiritcode` | Начать интерактивную сессию |
| `spiritcode login` / `logout` | Сохранить или удалить локальный ключ |
| `spiritcode models` | Получить каталог моделей |
| `spiritcode account` | Показать аккаунт |
| `spiritcode sessions` | Список сохранённых сессий |
| `spiritcode resume <id>` | Продолжить сессию в её проекте |

В диалоге: `/help`, `/model`, `/profile`, `/balance`, `/subscription`, `/usage`, `/new`, `/sessions`, `/resume`, `/compact`, `/diff`, `/undo`, `/permissions`, `/exit`.

Через `@путь` пользователь может явно добавить файл в контекст. Это необязательная подсказка агенту, а не основной способ работы с проектом.

## 3. Архитектура клиента и конфигурация

### Отдельный Python-проект

Использовать Python 3.12+, пакетную структуру `src/spiritcode/`, `pyproject.toml` и console entry point `spiritcode`.

Стек:

- `argparse` и `asyncio` из стандартной библиотеки.
- `prompt_toolkit` для ввода, истории и автодополнения.
- Rich для Markdown, кода, таблиц и diff.
- HTTPX для HTTP и асинхронного streaming.
- Pydantic для сетевых моделей и аргументов инструментов.
- `platformdirs` для пользовательских каталогов, `keyring` для ключей.
- SQLite из стандартной библиотеки для сессий.

Разделить CLI, интерфейс, API-клиент, цикл агента, инструменты, разрешения, контекст и хранилище сессий. Не использовать фреймворк агентов: цикл выполнения небольшой и контролируется проектом.

### Конфигурация

Все изменяемые разработчиком настройки собрать в `config.py`: адрес SpiritLM, пути API и кабинета, цвета, ASCII-арт, таймауты, ограничения инструментов и значения по умолчанию.

Начальный адрес: `http://localhost:3000`, путь генерации — `/v1/chat/completions`. URL строить централизованно, исключая повторение `/v1`.

Предусмотреть:

- `SPIRITLM_BASE_URL` и `SPIRITLM_API_KEY` для окружения. Base URL означает адрес сервиса без `/v1`.
- Пользовательский TOML с выбранной моделью и настройками интерфейса.
- Приоритет: явный параметр CLI → окружение → пользовательские настройки → `config.py`.
- Ключи не хранить в `config.py`, TOML, сессиях или логах.
- При недоступном системном keyring использовать ключ из окружения либо только в памяти текущего процесса.
- HTTP разрешать для localhost; для удалённого сервиса требовать HTTPS.
- Не пересылать ключ при перенаправлениях на другой origin.

## 4. Контракт SpiritLM и серверные изменения

### Существующие возможности

Использовать `GET /v1/models` и `POST /v1/chat/completions` с Bearer-ключом SpiritLM. Responses и Anthropic Messages клиенту не нужны.

Каталог получать с сервера, без статического списка моделей. Все модели доступны для выбора; агентные инструменты передавать при подтверждённой или неизвестной поддержке function calling. Только явное отсутствие поддержки включает режим чата с понятным уведомлением. При отказе API запрос не повторять автоматически и предложить /model.

Проверенный код содержит тарификацию и подписки, но проектные инструкции требуют сохранять запрет клиентской генерации до готовности оплаты. Перед интеграцией подтвердить действующий серверный контракт; SpiritCode не должен обходить ограничения сервера.

### Новые серверные возможности

В текущем SpiritLM профиль и подписка защищены веб-сессией Clerk. Добавить отдельные маршруты с существующей авторизацией API-ключом:

| Маршрут | Данные |
| --- | --- |
| `GET /v1/account` | ID, отображаемое имя, email, дата регистрации, маскированный текущий ключ и его настройки финансирования |
| `GET /v1/account/balance` | Баланс в RUB |
| `GET /v1/account/subscription` | Текущий и будущие периоды, кредиты, резерв, даты окончания, ограничения |
| `GET /v1/account/usage?period=…` | Расход и токены за `2d`, `7d`, `30d` или `all` |
| `GET /v1/spiritcode/models` | Дополнительные сведения о моделях: tool calling, окно контекста, лимит вывода, цена и ограничения подписки |

Сохранить прежние маршруты и формат `/v1/models`. Дополнительные сведения брать из серверной конфигурации; неизвестные характеристики возвращать как `null`. Имя и email получать сервером через Clerk, не выдавая клиенту Clerk-секреты.

В новых маршрутах определять владельца по ключу, переиспользовать операции из `src/actions/`, возвращать `Cache-Control: no-store` и существующий формат ошибок. Финансовые значения — десятичные строки, даты — UTC ISO 8601. Тестовые подписки не показывать как рабочие.

Если расширения сервера ещё не развёрнуты, чат и каталог работают самостоятельно, а раздел аккаунта сообщает о недоступности функции.

Ссылки на кабинет строить от настроенного адреса SpiritLM и существующих маршрутов `/dashboard`, `/dashboard/subscription`, `/dashboard/keys`. Не создавать покупки или платежи из CLI.

## 5. Работа агента и инструменты

### Цикл выполнения

Сообщение пользователя → подготовка контекста → потоковый запрос → сбор вызовов инструментов → проверка аргументов и разрешений → выполнение → передача результатов модели → итоговый ответ.

Инструменты первой версии:

- Список файлов, текстовый поиск, чтение файла по диапазону строк.
- Создание файла и применение точечных правок.
- Выполнение команды в явно указанной директории.

Поиск реализовать на Python с учётом `.gitignore`; не требовать установленного `rg`. Git использовать при наличии, но поддержать обычные каталоги.

Собирать фрагменты `tool_calls` по индексу и ID. Исполнять только полностью полученный и проверенный вызов. Инструменты выполнять последовательно; ограничить один пользовательский ход 30 итерациями, затем предложить продолжение.

По умолчанию команды имеют таймаут 120 секунд, чтение и результаты инструментов ограничены по размеру с явным сообщением об усечении. В стандартном режиме увеличение лимита команды требует подтверждения.

### Разрешения и изменения файлов

- Чтение и правки внутри выбранного проекта разрешены автоматически.
- `/permissions` сохраняет режим глобально: стандартная защита,
  без защиты или полная защита. В стандартном режиме Git, удаление, перезапись,
  системные и непрозрачные команды требуют подтверждения; известные чтение и проверки — нет.
- Без защиты действует включённый по умолчанию чекбокс «Спрашивать перед удалением»;
  непрозрачный код также требует разрешения при включённом чекбоксе. При выключенном
  чекбоксе shell-команды выполняются без запросов. Полная защита спрашивает о каждой shell-команде.
- Чтение и точечные правки внутри проекта автоматические во всех режимах.
  Доступ файловых инструментов вне проекта требует подтверждения.
- Отказ передавать модели как результат инструмента, сохраняя диалог.
- Проверять фактические пути после разрешения симлинков.
- Исключать секреты, бинарные файлы, `.git`, зависимости и артефакты из автоматического сбора контекста. Чтение файлов секретов — только по отдельному разрешению.
- Передавать дочерним процессам окружение без ключа SpiritLM.
- Запросы разрешений считать контролем действий, а не системной песочницей: подтверждённая команда запускается с правами пользователя.

Правки применять только при совпадении ожидаемого исходного текста. Сохранять снимки изменяемых файлов для `/undo`. Отменять последнюю группу правок только если файлы с тех пор не менялись; команды через `/undo` не откатывать. Не использовать `git reset`.

## 6. Автоматический контекст и сессии

### Как агент получает файлы

Пользователь формулирует задачу обычным текстом. SpiritCode самостоятельно просматривает структуру проекта, ищет связанные участки кода и читает нужные файлы через инструменты. Ручное добавление через `@` не требуется.

Например, для задачи «исправь авторизацию» агент ищет связанные маршруты, компоненты и проверки, читает их, вносит изменения и предлагает запуск проверки.

Автоматически передавать инструкции `AGENTS.md`, краткую структуру проекта и состояние Git. Содержимое остальных файлов читать по необходимости, а не отправлять весь репозиторий в каждый запрос. Явное `@путь` добавляет выбранный файл с теми же проверками доступа и лимитами размера.

### Инструкции и хранение

- Корень проекта фиксируется при запуске: Git-корень, иначе текущий каталог.
- Учитывать корневой и вложенные `AGENTS.md`; вложенные инструкции действуют для своего поддерева.
- Сохранять сообщения, модель, корень проекта, события инструментов и снимки правок в пользовательском SQLite-хранилище.
- При восстановлении не повторять команды и незавершённые вызовы автоматически.
- Смену модели применять со следующего запроса, сохраняя переписку и заново оценивая контекст.

### Сжатие контекста

Автосжатие запускать при достижении примерно 75% доступного входного бюджета или перед превышением серверных лимитов. Сохранять цель, решения, изменённые файлы и незавершённые шаги; системные инструкции и актуальные `AGENTS.md` собирать заново.

Сжатие выполняется отдельным оплачиваемым запросом с видимым уведомлением. При неизвестном окне контекста использовать консервативный бюджет 16 000 токенов и явно помечать оценку; при ошибке сжатия сохранять исходную историю.

## 7. Сеть, отмена и учёт расходов

- Без автоматических повторов платных генераций.
- Общий лимит запроса 100 секунд при текущем серверном лимите 90 секунд; настройки централизованы.
- Разбирать SSE с учётом дробления UTF-8, CRLF, ошибок внутри потока и отсутствующего финального события.
- При отмене закрывать HTTP-поток и останавливать текущую команду вместе с дочерними процессами.
- Показать серверный request ID для диагностики.
- Неизвестный usage отображать как неизвестный. Стоимость по каталогу обозначать оценкой; фактические списания получать с сервера.
- Не переключать модель и не разрешать списание с баланса автоматически при исчерпании подписки.
- Ошибки показывать понятным русским текстом без ключей и приватных ответов поставщика.

## 8. Этапы реализации

1. Создать отдельный репозиторий SpiritCode, перенести этот документ и исходную иконку как референс, зафиксировать цвета.
2. Реализовать в SpiritLM маршруты аккаунта и метаданные моделей; зафиксировать JSON-примеры успешных ответов и ошибок.
3. Собрать оболочку клиента: установка, `config.py`, вход, ASCII-шапка, каталог, выбор модели и потоковый чат.
4. Реализовать агент: инструменты, разрешения, команды, diff, снимки и отмена правок.
5. Добавить сохранение и восстановление сессий, `AGENTS.md`, автоматический поиск файлов, автосжатие и просмотр аккаунта.
6. Подготовить CI для трёх ОС, README и сборку Python-пакета; проверить локальную установку через `uv tool` и pipx. Публикация пакета — отдельный шаг.

Серверная часть остаётся в репозитории SpiritLM; Python CLI разрабатывается отдельно. Для переноса плана достаточно этого файла, исходной иконки и согласованного серверного контракта.

## 9. Проверки и критерии готовности

Проверки клиента: pytest, Ruff и mypy. Все автоматические запросы к моделям мокировать.

Обязательные сценарии:

- Неверный и отозванный ключ, недоступный keyring, отсутствие сервера.
- Выбор модели, смена модели, модель без инструментов, ограничения подписки.
- Разбитые SSE/tool calls, повреждённые аргументы, обрыв, таймаут и отмена без повторной генерации.
- Задача без `@`: автоматический поиск → чтение → правка → подтверждённая команда → итоговый ответ.
- Явное прикрепление файла через `@` и соблюдение ограничений доступа.
- Отказ в разрешении, выход за корень, симлинки, изменённый пользователем файл и безопасный `/undo`.
- Восстановление после сбоя без повторного выполнения инструментов.
- Сжатие контекста с сохранением цели и инструкций.
- Нулевая и отсутствующая подписка, неизвестный usage, точное отображение денежных строк.
- Узкий терминал, кириллица, вставка многострочного текста, `NO_COLOR`, перенаправление вывода и восстановление терминала после выхода.

Для серверных изменений выполнить `npm run typecheck`, `npm run lint`, `npm run test:unit` и `npm run test:backend` на доступной мигрированной тестовой БД. `npm run build` не запускать. Реальные платные генерации выполнять только по отдельному запросу.

Первая версия готова, когда SpiritCode устанавливается на трёх ОС, входит по ключу, получает модели SpiritLM, самостоятельно находит нужные файлы, выполняет задачу с правками и подтверждённой командой, возобновляет сессию и показывает реальные данные аккаунта.
